### Store: capture ingest (`spikes/w0-sqlite-android`)

- `LocalStore::ingest(media_dir, staff_id, bytes)`:
  - Checks the size (1 byte to 25 MB).
  - Identifies the type from the file signature, not a client claim: JPEG, PNG or WebP only (Spec §5).
  - Hashes the bytes with SHA-256.
  - Writes `<sha256>.<ext>` atomically (temp file, `fsync`, rename), so identical photos are stored once.
  - Queues a `pending` capture with a UUID v4 `client_id` and an RFC 3339 millisecond UTC timestamp, taken where
    the record is built.
- Migration `0002` adds `media_mime` and `media_bytes` (Spec §5 "Media Assets").
- New `list_recent` and `counts` back the History and Home screens.

### App (`nocapsnap/app`)

- **Stack:** SvelteKit 2.70 / Svelte 5.57 (runes), built as a static SPA with `adapter-static`; every route is
  prerendered. Tauri 2.12; Vite 8; pnpm 10.34.
- **Rust core** (`src-tauri/src/lib.rs`) exposes five commands:
  - `store_status`
  - `capture_ingest`: the photo arrives as the raw IPC body, with no base64 step.
  - `list_captures`
  - `run_selftest`: the W0 round trip, run inside the app's private data directory.
  - `simulate_ack`: spike only; it stands in for the server so the "Synced · QR ready" state can be checked.
- **Security settings:**
  - Capability `core:default` only. No fs, shell, HTTP or other plugins (Spec §6).
  - The CSP is `'self'` for scripts, with no remote origins anywhere. `style-src` keeps `'unsafe-inline'` with
    Tauri's hash injection turned off, because Svelte and SvelteKit emit inline style attributes.
- **Android** (`src-tauri/gen/android`), generated by `tauri android init`:
  - Package `com.hammurabicoding.nocapsnap`; compileSdk/targetSdk 37 (Tauri 2.12's template default, which meets
    "API 36+"); minSdk 24.
  - Manifest: `CAMERA` added for the in-app viewfinder, with the camera feature marked required.
  - The template's **Android TV declarations were removed**; leaving them would make Play list and review CapSnap
    as a TV app.
- **Preview mode:** outside Tauri, the bridge switches to an in-memory implementation behind a "Browser preview ·
  nothing is saved" ribbon, so the UI can be reviewed in a desktop browser (`pnpm dev`).

### Design language (owner direction)

"The pass at a quiet, very good restaurant." Tokens are in `app/src/app.css`.

| Element | Asian-fusion material | Midwestern plainness |
|---|---|---|
| Background | Washi paper `#F4EEE2`, faint fibre grain drawn inline as SVG noise (nothing fetched) | — |
| Text | Sumi ink `#1D1915`, serif headlines from the phone's own serif (Noto Serif on Android) | Plain, specific copy: "It stays on this phone until the server confirms it" |
| Primary action | Urushi lacquer `#9A2B22` | 52 px targets for wet or gloved hands |
| Pending / synced | Aizome indigo (also denim) / matcha | The spec's exact wording: "Saved offline · QR not ready", "Synced · QR ready" |
| Accents | Kintsugi gold hairlines and corner marks | Walnut kickers, no ornament that doesn't do a job |
| Signature moments | A hanko seal wordmark; a "Saved · on this phone" stamp pressed onto the photo; an ensō-stroke shutter | A plate-from-above guide showing where the dish goes |
| Night service | A dark theme from the same materials (`prefers-color-scheme`) | — |

There are no external fonts, images or scripts (Spec §6). Headlines use the device's serif font; there are no
webfont files.

Screens: **Home** (service line, today's plates / waiting / QR ready), **Capture** (a choice between two camera
routes → live viewfinder with the shutter over the image → review → stamped receipt), **History** (grouped by
day, a status pill per plate) and **Manager** (Phase 3 placeholders plus the W1 device check).

## Camera: what the code says (wry 0.57.0, `RustWebChromeClient.kt`)

| Route | Mechanism | Permission behaviour (read from source) |
|---|---|---|
| **A — In-app viewfinder** | `getUserMedia` in the WebView | `onPermissionRequest` maps `RESOURCE_VIDEO_CAPTURE` to `Manifest.permission.CAMERA` and asks for it at runtime at that moment. It only works if `CAMERA` is declared in the manifest. |
| **B — Phone camera** | `<input type="file" accept="image/*" capture="environment">` | `onShowFileChooser` launches `MediaStore.ACTION_IMAGE_CAPTURE` directly when `isMediaCaptureSupported`, meaning `CAMERA` is granted **or not declared at all**. If it is declared but not granted, it asks first. |

So route B can run with **no runtime permission**, provided the manifest doesn't declare `CAMERA`. That is the
strongest reading of Spec §6's permission minimisation (D5). W1 declares `CAMERA` so both routes can be compared
on the same APK. The device checklist below records how each behaves.

## Device checklist (owner, about 10 minutes, Android 16 phone with USB debugging)

```bash
adb install -r nocapsnap/app/src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk
```

1. Open CapSnap. The masthead and tab bar should not sit under the status bar or navigation bar.
2. **Capture → In-app viewfinder → Start camera.** The Android camera prompt should appear only now. Allow it.
   Take a photo, then **Save plate**. Expect the "Saved offline" stamp.
3. **Capture → Phone camera → Open camera app.** The system camera should open. Take a photo. It should come back
   to Review. Save it.
4. Repeat step 3 after denying camera permission in Settings. Record whether the system camera still opens.
5. **Manager → Run storage self-test.** Expect `ok sqlite=3.51.3 journal=wal … · app sandbox`.
6. **Manager → Simulate server sync**, then **History**: one plate should show "Synced · QR ready".
7. Force-stop the app, reopen it, and check **History**: every plate should still be there (on-device persistence).

Report back for each step: pass or fail, plus a screenshot of anything that looks wrong.

## Tenth Man

- **Still zero execution on Android.** The APK builds, but the WebView camera bridge, the system-camera round trip,
  SQLite inside the sandbox, the insets and the serif fallback were never observed on a phone. W1 cannot pass the
  spec's hard gate by itself. That needs the device checklist.
- **The design was judged in desktop Chromium.** Android WebView versions, OEM serif fonts (Noto Serif versus
  Samsung's) and dark-mode forcing (`FORCE_DARK`) may render differently.
- **The ensō, hanko and washi motifs are my interpretation of a one-line brief.** They risk reading as themed
  rather than refined. The owner should judge them on a real phone before W2 builds more screens on them.
- **Preview mode ships in the same bundle.** It is chosen at runtime by the presence of Tauri, so the in-memory
  bridge is dead code on the device. W2 should strip it from release builds.
- **`simulate_ack` is a fake server acknowledgement inside the app.** It must be removed before any beta (W5),
  or it could mark plates synced that never reached the server.
- **targetSdk 37 was taken from Tauri's template.** The spec says "36+", so it is compliant, but it opts into
  Android 17 behaviour changes that haven't been tested.
- **Rust file IO in `ingest` is blocking inside an async command.** That's fine for single photos; W2 should move it
  to `spawn_blocking` before batch sync.
- **The app depends on a crate under `spikes/`.** W2 should promote it to `crates/capsnap-store`.
- **`CAMERA` is declared for the comparison.** If D5 picks route B only, keeping the declaration adds a
  permission Play will ask the owner to justify in Data safety.
